# 履歴をリングバッファにする (**いまは入れていない**)

当たり判定で遡るための履歴 (`server/relay.ts` の `recordPose`) は、素の配列に
`push` して溢れたら `shift` している。毎 tick・人数ぶんの `Pose` を作って捨て、
`shift` で 28 要素を詰め直している。

**作って測って、入れないことにした。** 実装は
[history-ring-buffer.patch](./history-ring-buffer.patch) に取ってある
(`git apply docs/notes/history-ring-buffer.patch` で戻る)。

## 測った値

満席 8 人・64Hz で 12 秒回して `/health` を読む
(`bun run tools/measure/load.ts 8`)。3 回ずつ。

|              | 平均                | 最悪                   | heap |
| ------------ | ------------------- | ---------------------- | ---- |
| いまの配列   | 0.03 / 0.03 / 0.02ms | 0.25 / 0.22 / 0.18ms | 4MB  |
| リングバッファ | 0.02 / 0.02 / 0.02ms | 0.37 / 0.18 / 0.13ms | 3MB  |

刻みの上限は 15.6ms (64Hz)。**平均は上限の 0.19% が 0.13% になる。**

- **平均は下がる。** ただし表示が小数 2 桁なので、実際の差はこれより小さい
- **heap は 1MB 減る。** 確保が消えた効果として素直に読める
- **最悪は差が読めない。** 回ごとの揺れ (0.13〜0.37ms) のほうが両者の差より
  大きい。**GC の山が出ると思って探したが、12 秒・4MB では出なかった**

## なぜ入れないか

効果は実在するが、**上限に対して誤差**。引き換えにコードが増える (書き込み
位置・埋まっている数・古い順に並べ直す関数・並べ直す先の器)。

## いつ入れるか

- **定員を 8 人から増やしたとき。** 確保も詰め直しも人数に比例するので、
  32 人なら 4 倍になる (それでも 0.08ms だが)
- `/health` の「刻み 平均」が 1ms を超え始めたとき

どちらも `tools/measure/load.ts` で前後を比べられる。**測らずに入れない。**

## 入れるときの注意

- **`HISTORY_SIZE` を 2 の冪に固定しない。** `%` を `&` に替えて浮くのは
  1 tick あたり数ナノ秒だが、**窓 (`LAG_WINDOW_MS`) と切り離れる**。20Hz の頃に
  「12 個」と手で書いてあったのを 64Hz へ上げたときに直し忘れて、0.19 秒しか
  遡れていなかった前科がある。窓は 0.4 秒あるのに半分より前が届かず、遠い人ほど
  「当てたのに通らない」が静かに増えていた
- **並べ直す先を 1 本で使い回さない。** `verifyHit` は撃った側と撃たれた側を
  同時に見るので、2 度目の呼びが 1 度目を潰す。器は呼ぶ側が持つ
- 申告のたびに 28 要素を書き写す仕事が**増える**。毎 tick から仕事を削って、
  申告のたびへ積む形になる (連射中は 1 人あたり毎秒 10 回前後)
